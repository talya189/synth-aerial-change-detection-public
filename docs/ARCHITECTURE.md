# Architecture and roadmap: synthetic aerial change detection

This document answers the project brief: Python + JSON + .blend, T1/T2 change detection, and LLM-ready edits. **First region: a settled rural landscape** with vegetation, buildings, asphalt and dirt roads and footpaths (eastern Galilee, the Korazim / Rosh Pina area). The Negev desert comes later, as a second scene type. It builds on what already exists in this repository (stages 1–4 and template step 1, all validated by rendering). It does not start over.

## 1. The three components

```
┌──────────────────────────────┐   writes    ┌───────────────────────────────┐
│ PYTHON: procedural logic     │ ──────────► │ JSON: scene spec              │
│ synth/planner, synth/prep    │             │ scenes/<id>/spec.json         │
│ terrain, roads, parcels,     │ ◄────────── │ every entity: stable id, kind,│
│ buildings, vegetation rules, │  edit ops   │ exact geometry, asset refs,   │
│ validation (slopes, overlap) │             │ seeds; environment; cameras;  │
└──────────────────────────────┘             │ history of modifications      │
                                             └──────────────┬────────────────┘
                                                            │ build / sync
                                                            ▼
                         ┌──────────────────────────────────────────────────────┐
                         │ BLENDER: generated geometry, materials, camera,      │
                         │ lights, render setup  (scenes/<id>/<epoch>.blend)    │
                         │ built by synth/blender from template.blend (assets,  │
                         │ prepared trees, scatter node group)                  │
                         └──────────────────────────────────────────────────────┘
```

**Python decides *what* goes *where*.** Its rules: roads follow terrain under a grade limit, houses go on gentle slopes facing streets, vegetation follows wetness and slope, nothing overlaps.

**JSON is the single source of truth.** It holds every building, road, tree group and path with a persistent id, its exact position and parameters, and its asset references. It also holds the environment (season, date, time, haze), the cameras, the seeds, and the list of modifications.

**Blender holds the result:** geometry, materials, lights and cameras, rebuilt reproducibly from spec + DEM + assets.

How countable and mass objects are handled:
- **Countable objects** (buildings, roads, paths, trees, shrub clusters) are listed one by one in the spec. Change detection and LLM edits need to address them individually ("the northern building").
- **Mass "stuff"** (grass tufts, pebbles, small stones: tens of thousands) is described by parameters plus a seed (density, clustering, slope range) and generated by the scatter node group. This keeps the spec small and the build fast (validated: build 80 s → 5 s), while still being exactly reproducible.

## 2. Editing an existing scene without regenerating everything

```
spec_T1 ──edit ops──► spec_T2      e.g. {"op": "add_building", "near": "road_002", "floors": 2}
   │                     │         Python validates each op against the same rules
   ▼                     ▼         (slope, overlap, road access) before it is applied
T1.blend  ──sync──►  T2.blend      sync = diff the two specs by entity id; rebuild only the
                                   added / removed / changed objects and the terrain patches
                                   under them; everything else stays bit-identical
```

The edit operations (add / remove / move / modify entity; set season / time / camera) are a small JSON command language with a schema. An LLM later only has to translate a sentence into these commands. No Blender scripting is needed, and every command is validated before it touches the scene.

## 3. Change detection outputs (fixed camera first)

For each pair:
- `T1.png`, `T2.png`;
- semantic masks for T1 and T2;
- instance masks;
- binary change mask;
- semantic change mask (from-class → to-class);
- `changes.json` (each structural change: op, entity id, before/after, pixel area).

**Structural vs environmental.** Change masks come only from geometry and label differences, never from pixel differences. A season or lighting change alters the RGB but produces an empty change mask, and is recorded as `environmental` in the metadata. Pairs with environment-only differences serve as hard negatives.

## 6. Main technical challenges

| Challenge | How it is addressed |
|---|---|
| 30 m DEM vs sub-metre pixels | Cubic upsampling plus band-limited micro-relief tapered at the core edge; built features (road cuts, terraces) edit the terrain. Validated. |
| Looking real, not "randomly populated" | Rule-based placement (routing under grade limits, parcels facing streets, wetness/slope-driven vegetation), checked on plan maps and renders at every step. |
| Rural specifics (Galilee first, Negev later) | Dry-season grassland, fields and terraces, pine groves and yard trees, village houses with rooftop equipment; later: desert ground, wadis, acacias, Bedouin structures. Several need assets: see section 7. |
| Pixel-exact labels | Object Index pass (unfiltered); class/instance tables; round-trip-checked PNGs. Validated, and a past write bug was caught and fixed. |
| T1/T2 consistency | Stable entity ids and per-entity RNG streams: unchanged objects are identical. Diff-based sync rebuilds only what changed. Fixed camera first, pixel-aligned. |
| Structural vs environmental change | Change masks from labels/geometry only; environment recorded separately. |
| Speed on an M2 laptop | Scatter as node instances, persistent render data, thinned tree geometry: scene build ~5 s; previews ~2 min. |
| Blender 5.2 quirks | Documented in code: modifier inputs API, Metal crash workaround plus retry, instancing vs labels. |
